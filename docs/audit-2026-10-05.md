## Зовнішні обмеження

Поточний API повернув операторів `dnipro-dnem` та `dnipro-cek`.
Він не повернув регіон `dnipropetrovska-oblast`.
Для Києва API повернув черги `1.1`–`60.1`, але не `1.2`.
Не можна автоматично вибрати оператор або замінити чергу користувача.
Потрібне зрозуміле повідомлення про недоступний графік і повторне налаштування.
Повторні записи однакової помилки треба обмежити.

Поле `date_today` API містило `2026-07-01`.
Водночас графіки ІФ містили ключ дати `2026-10-05`.
Тому не можна визначати придатність графіка лише за полем `date_today`.
Перевіряти фактичні ключі дат. Не перейменовувати старі дні на сьогодні.

## Результати реалізації

Користувач дозволив виконати роботу без Gemini.
Агент `gpt-6-luna` виконав основну реалізацію.
Codex перевірив код та доповнив виправлення.

- Matplotlib працює в одному окремому потоці. Скасування запиту не запускає паралельну побудову.
- Динамічний графік об'єднує сусідні хвилини одного кольору. Межі статусів залишаються точними до хвилини.
- Клієнт застосовує налаштований TTL. Одночасні запити очікують одне оновлення кешу.
- Загальне оновлення має межу 45 секунд. Повторна спроба після завершення має паузу 15 секунд.
- ІФ виконує максимум чотири запити одночасно. Пакет має межу 15 секунд.
- Тайм-аут пакета зберігає вже отримані черги. Помилка загального оновлення зберігає попередній кеш.
- Новий кеш, ETag та хеші стають доступними разом після успішної обробки.
- Відповідь 304 також оновлює службові дати. Код зберігає фактичні ключі дат графіка.
- Кеш PNG зберігає максимум 100 записів. Нова версія замінює стару версію тієї самої черги й режиму.
- Код зберігає хеш доставки після успішного надсилання всіх графіків.
- Невідомі та часткові дані отримують відповідне попередження.
- Код перевіряє формат і час локального джерела та Gist. Застарілий локальний файл не приховує свіжий Gist.
- Нагадування враховують лише майбутні події. Статус `unknown` не означає відновлення живлення.
- PNG містить ID черги. Особистий підпис містить екрановану назву користувача.
- Polling починається без очікування початкової розсилки. Завершення закриває фонові задачі й сесії.
- Журнал містить час отримання даних, побудови PNG, надсилання та всієї відповіді.
- Контрольна задача записує `Event loop delay`, якщо затримка перевищує дві секунди.

## Серверна перевірка

Сервер ще не запускав виправлений код у межах цієї перевірки.
Після встановлення коміту треба перезапустити службу й запитати «Поточний статус».
Команда показує журнал служби за інтервал початкової затримки:

```bash
sudo journalctl -u svitlo_bot.service --since "2026-10-05 04:08:00 UTC" --until "2026-10-05 04:16:00 UTC" --utc -o short-iso-precise --no-pager
```

Параметр `-k` показує журнал ядра. Він не показує журнал бота.
Якщо journald вже видалив записи, ця команда не відновить їх.

Команда для нового запиту:

```bash
sudo journalctl -u svitlo_bot.service --since "10 minutes ago" -o short-iso-precise --no-pager
```

Треба порівняти `Schedule data`, `Image generation`, `Image renderer wait`, `Telegram schedule send` та `Schedule response`.
Запис `Event loop delay` допоможе відрізнити затримку основного циклу від очікування мережі.

## Обмеження, що залишилися

Список операторів і черг залежить від зовнішнього API.
Користувач має повторно вибрати недоступний оператор або чергу через `/start`.
Код не підміняє оператора автоматично.

Кеш зберігає відомі статуси, коли нове джерело повертає `unknown`.
Це наявна політика збереження даних. Вона потребує окремої політики максимального віку при тривалому збої джерела.

Наявна перевірка релевантності пропускає графік без майбутніх відключень, якщо історія втрачена.
Через це скасування відключення після перезапуску може не створити сповіщення.
Повне виправлення потребує збереження останнього надісланого стану користувача в SQLite.
Ця зміна потребує окремої міграції та узгодження поведінки.

Час графіка залежить від системного часового поясу.
Сервер має використовувати `Europe/Kyiv` або еквівалентний налаштований часовий пояс.
